# 突发情况应急手册

> 面向能源综合防御赛防守方的「现场 SOP」，覆盖比赛中高频突发情况。每节自包含，可对照步骤立即执行；命令均为 root/admin 执行，先取证后清理，动作顺序遵循「先止损、再溯源、后加固」。

## 靶机被攻破扣分后的 15 分钟处置流程

触发信号：面板告警、flag 被拿走、平台提示某题被攻破；思路：先断入口，再溯源，再加固，最后抢答题权限。

1. **0-3 分钟断入口**：封攻击源 IP（Linux `iptables -I INPUT -s <攻击IP> -j DROP`；Windows 防火墙入站规则封源 IP），若入口为 Web 则 `systemctl restart tomcat nginx` 踢掉已建立的攻击连接。
2. **4-6 分钟清驻留**：`ps -ef | grep -Ei 'nc|bash -i|xmrig'` 命中即 `kill -9 <pid>`，清除可疑计划任务 `crontab -l`。
3. **7-10 分钟溯源**：`last`、`grep Accepted /var/log/secure`、`find /var/www -type f -mmin -30`，锁定攻击时间线与入口，`cp` 取证文件到 /root/evidence 并截图存档。
4. **11-13 分钟加固**：执行一键加固（锁空口令、清可疑计划任务、收紧 Web 目录权限），`passwd` 改本地口令，封非必要入端口。
5. **14-15 分钟抢答题权限**：题目开放后立即到平台作答——衰减公式 P=S×L/[N+(L-1)]，越早解出分数越高；同时按 06-Writeup 模板开始写证据链报告。

## 业务服务崩溃/打不开的快速恢复

1. **绕过 WAF 直测**：`curl -i http://127.0.0.1:8080/` 直连业务端口；通则查 WAF 日志命中项（误杀见「WAF 误杀」节），不通进下一步。
2. **查服务与端口**：`systemctl status <服务>`、`ss -tlnp | grep -E '8080|3306'`、`ps -ef | grep <服务名>`，服务停了 `systemctl restart <服务>`。
3. **看启动失败原因**：`journalctl -u <服务> -n 50`，常见配置错误/端口被占/依赖没起，按报错修复。
4. **查资源瓶颈**：`df -h`（磁盘满）、`free -h`（内存耗尽）、`top`（CPU 被打满），分别清理大日志/杀高占用进程。
5. **回滚配置/恢复文件**：配置被改则 `cp /backup/xxx.conf /etc/xxx.conf && systemctl restart xxx`；文件被删则从备份 `tar xzf` 恢复对应目录。
6. **验证业务**：`curl -I http://127.0.0.1:8080/` 返回 200 且内容正常才算恢复；Windows 用 `sc query <服务>` / `net start <服务>` / 事件查看器。

## 发现 Webshell 的处置流程

1. **定位（只读不动）**：`find /var/www /tmp -type f \( -name '*.php' -o -name '*.jsp' -o -name '*.war' \) -mmin -120`。
2. **特征扫描**：`grep -rlE 'eval\(|base64_decode|assert\(|\$_POST|system\(' /var/www/`，缩小到具体文件。
3. **取证**：`mkdir -p /root/evidence && cp <webshell> /root/evidence/`，记录 `stat` 时间戳、`grep <webshell名> /var/log/nginx/access.log` 找到上传请求与来源 IP。
4. **隔离**：把文件移出 Web 目录到取证目录（平台自动隔离到 logs/quarantine/，手工 `mv` 亦可），**勿直接删除**，保留证据。
5. **清残留**：删除同目录其他新增文件、`/tmp/*.tmp` 上传临时文件、可疑 session 文件。
6. **查同源**：`crontab -l`、`/etc/rc.local`、`~/.ssh/authorized_keys`、`systemctl list-unit-files` 检查是否被种入持久化后门，一并清除。

## 发现反弹 Shell 的处置流程

1. **排查**：`ss -tnp | grep -E 'ESTAB|SYN'` 看外连（对非业务 IP/非常规端口警惕）；`ps -ef | grep -E 'bash -i|/dev/tcp|nc |ncat|python.*socket'`。
2. **kill**：`kill -9 <pid>`，再 `pkill -9 -f 'nc -e'`；杀不掉且 pid 反复更换说明有守护进程，逐级清父进程。
3. **杀不死就重启承载进程**：父进程是 php-fpm/apache 则 `systemctl restart php-fpm`，切断 shell 与攻击者通道。
4. **封端口/目标 IP**：`iptables -I OUTPUT -d <外连IP> -j DROP`，封反弹常用端口 4444/5555/6666：`iptables -I OUTPUT -p tcp --dport 4444 -j DROP`。
5. **查父进程来源**：`lsof -p <pid> | grep cwd` 看启动目录，找被种下的 crontab/rc.local/systemd unit 启动项并清除。
6. **收尾**：`history -c` 清理本机痕迹，按攻击源 IP 与反弹目标 IP 写溯源证据。

## 挖矿病毒清理

1. **定位**：`top -c` 找高 CPU 进程 → `ps -ef | grep <pid>` 拿完整命令与路径 → `ls -l /proc/<pid>/exe` 定位二进制。
2. **杀进程**：`kill -9 <pid>`；自动重启则查守护者（父进程为 crond/开机脚本时先清守护再杀本体）。
3. **删文件**：`rm -f /tmp/<挖矿二进制>`，`find /tmp /var/tmp -type f -mmin -60` 清其余新文件。
4. **清计划任务**：`crontab -l` 删异常行；查 `/etc/cron.d/`、`/etc/crontab`、`/var/spool/cron/`、`systemctl list-timers`、`/etc/profile.d/*.sh` 中被注入的启动脚本。
5. **封矿池 IP/端口**：`iptables -I OUTPUT -d <矿池IP> -j DROP`，批量 `iptables -I OUTPUT -p tcp --dport 3333 -j DROP`（4444/5555/14444 同）。
6. **确认收敛**：`top` CPU 回落、`ss -tnp` 无异常外连、`df -h` 磁盘不再增长即处理完成。

## 勒索/文件被加密

1. **隔离断网（第一原则）**：`ip link set eth0 down`（或拔网线/断交换机端口），停止勒索进程继续加密与回传，全体暂停写操作。
2. **查扩散源**：`ps -ef` 找可疑进程（随机名、高 CPU）→ `lsof -c <pid>` 看它正在改哪些文件 → 定位最早被加密文件对应进程即源头。
3. **评估备份恢复**：有备份则 `rsync -av /backup/ /业务目录/` 或回滚 VMware 快照；无备份立即把未加密文件 `cp` 到外置盘/其它机器抢救。
4. **留证据**：勒索说明、被加密样本、进程路径 `cp` 到取证目录，记录 `ss -tnp` 网络连接，保留原件勿删。
5. **修复入口**：清除被利用的 WebShell/弱口令，改全部口令，再恢复网络与业务。

## 暴力破解登录

1. **定位源 IP**：`grep 'Failed password' /var/log/secure | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head`（Ubuntu 用 `grep sshd.*Failed /var/log/auth.log`）。
2. **Windows 定位**：`Get-WinEvent -FilterHashtable @{LogName='Security';Id=4625} | ForEach-Object { $_.Properties[18].Value } | Group-Object | Sort-Object Count -Descending`。
3. **封源 IP**：`iptables -I INPUT -s <IP> -j DROP`，有 fail2ban 则 `fail2ban-client set sshd banip <IP>`；Windows：`New-NetFirewallRule -Direction Inbound -RemoteAddress <IP> -Action Block`。
4. **改口令**：`passwd <被爆破用户>`，root 与疑似泄露账号一并改。
5. **限速/禁 root**：/etc/ssh/sshd_config 设 `MaxAuthTries 3`、`PermitRootLogin no`、`PasswordAuthentication no` → `sshd -t && systemctl restart sshd`；开启 fail2ban sshd jail。
6. **Windows 加固**：禁用空口令账户，组策略设账户锁定阈值 5 次（安全选项→账户锁定策略）。

## 横向移动/内网扫描

1. **查异常连接**：`ss -tnp | grep -E '192.168.253|:445 |:22 '`、`arp -a` 看新增 MAC、`last` 看兄弟靶机登录记录；Windows 查 4624 登录事件源。
2. **判断是否被当跳板**：`grep -E 'Accepted|Failed' /var/log/secure | grep <兄弟靶机IP>`，确认攻击链走向。
3. **封扫描源与端口**：`iptables -I INPUT -s <扫描IP> -j DROP`；非业务端口一律封：`iptables -I INPUT -p tcp --dport 445 -j DROP`、`--dport 139 -j DROP`；Windows 禁用 SMB：`Set-NetFirewallRule -DisplayGroup 'File and Printer Sharing' -Enabled False`。
4. **改凭据**：改本机全部口令，清理 `~/.ssh/authorized_keys` 中被植入的兄弟机公钥，删除已建立的信任关系。
5. **清后门**：`crontab -l`、启动项、新增服务 `systemctl list-unit-files` 一并排查清除。
6. **写溯源**：按「入口机→跳板→目标机」链路写横向移动溯源，附连接日志截图。

## 历史流量回放攻击的应对

1. **抓包分析**：`tcpdump -i any -nn -s0 -w /root/evidence/replay.pcap`，先确认回放窗口（按题目开放时间倒推），`tshark -r replay.pcap -Y 'http.request'` 看请求序列与操作对象。
2. **对比基线**：`find /etc /var/www -type f -mmin -240`、`systemctl list-unit-files` 看新增服务、`ss -tlnp` 看新增监听、`cat /etc/passwd` 看新增用户、`crontab -l` 与开赛快照 diff。
3. **恢复被改配置/文件**：CentOS `rpm -V` 校验系统文件、Ubuntu `apt-get install --reinstall <包>`、配置直接 `cp /backup/xxx /etc/xxx`，随后重启受影响服务。
4. **针对性修复**：回放若关了防火墙/放行 SSH，恢复后立即落库 `iptables-save > /etc/sysconfig/iptables`、`firewall-cmd --runtime-to-permanent`。
5. **建基线防再犯**：对关键配置文件生成 `sha256sum` 快照存入外置文件，轮询比对，发现被改立即告警并自动恢复。

## 磁盘爆满/日志洪水

1. **定位大目录**：`du -h --max-depth=1 / | sort -hr | head` 逐级下钻，重点看 /var/log、/tmp、Web 上传目录。
2. **定位大文件**：`find / -type f -size +500M -exec ls -lh {} \;`。
3. **查洪水来源**：`ls -lhS /var/log/* | head`，`tail -n 50` 确认内容——扫描器刷屏则配合封源 IP，后门循环写则清后门。
4. **清理与轮转**：`logrotate -f /etc/logrotate.conf` 手动轮转，或先备份后清 `: > /var/log/xxx.log`，`rm -f /tmp/core.*`、旧 `/var/log/*.gz`。
5. **配 logrotate**：/etc/logrotate.conf 设 `maxsize 100M`、`rotate 4`，高频日志单独加 `daily` + `compress` + `copytruncate`（不中断服务）。
6. **收敛判定**：`df -h` 回到安全水位、`du /var/log` 稳定，并判断是否由攻击导致（回放/后门）补加固。

## WAF 误杀导致业务不可用

1. **切 alert 模式**：面板关闭 block_mode（仅告警不拦截），或改配置 `[rules] block_mode = false` 重启，立即恢复业务可用。
2. **临时放行白名单**：对确认为正常业务的路径/源 IP 加白名单（如放行 /login 接口、放行内网维护 IP），保答题流程可用。
3. **恢复并验证业务**：确认关键接口 200 正常（登录、查询、flag 提交前置流程全跑一遍）。
4. **收紧回归**：恢复 `block_mode = true`，逐条 review 告警日志中被拦样本，把误杀路径细分加白，再逐步打开对应规则。
5. **冒烟测试**：每收紧一批规则做一轮 curl 冒烟，确认业务与拦截并存后结束；全程保留「被拦样本→白名单→放行」的记录进报告。
